# CSC316 — HW#1: Password Protection

A small command-line program that stores the same user registration three different
ways, so the security difference between them can be observed directly:

| Table | What is stored | Security |
|-------|----------------|----------|
| Table 1 | the password exactly as typed | none |
| Table 2 | `SHA-256(password)` | better, but vulnerable to pre-computed tables |
| Table 3 | `SHA-256(salt + password)` with a unique per-user salt | the goal of this assignment |

---

## Running it

Python 3.8 or newer. No third-party packages, nothing to install.

```
python3 password_protection.py
```

Registrations are written to `password_db.json` in the same folder. That file is
deliberately excluded from this repository via `.gitignore`, because it holds
plaintext passwords.

### Menu

| Option | Description |
|--------|-------------|
| 1 | Register a user, then print all three stored representations |
| 2 | Display the full contents of all three tables |
| 3 | Log in — verifies the password against each table independently |
| 4 | Offline dictionary-attack demonstration (Table 2 vs Table 3) |
| 5 | Reset the database |
| 0 | Exit |

---

## Data structures

**Table 1 — plain**
`user_id` / `username` / `timestamp` / `password_plain`

**Table 2 — hashed**
`user_id` / `username` / `timestamp` / `password_hash`

**Table 3 — salted hash**
`user_id` / `username` / `timestamp` / `salt` / `password_salted_hash`

`timestamp` is the moment of registration. The assignment permits this extra
column, and Table 3 needs it as an input to the salt.

---

## Hashing

All hashing uses Python's standard-library `hashlib` module with **SHA-256**. No
hash function is implemented by hand, as required.

```python
def sha256_hex(text):
    return hashlib.sha256(text.encode("utf-8")).hexdigest()
```

Every digest is stored as a 64-character lowercase hex string.

---

## Salt construction

```
salt = SHA-256(username + user_id + timestamp)
```

The assignment asks for a deterministic, explainable salt rather than a random
one, so that the mechanism is visible. No random number generator is used
anywhere in the program.

**Why the salt is still unique per user.** `user_id` is a UUID version 4
generated by Python's `uuid` module, and `timestamp` is captured at microsecond
resolution at the instant of registration. Both are unique per registration on
their own, so their concatenation is too — even if the same person registers the
same username twice, the two salts differ. Uniqueness therefore does not depend
on the username being unique.

**Production note.** Real systems should generate salts from a cryptographically
secure source such as `secrets.token_bytes()`, and should use a slow,
purpose-built password hash — bcrypt, argon2, or PBKDF2 — rather than raw
SHA-256. SHA-256 is fast, which is exactly what an attacker wants when running
billions of guesses on a GPU. The deterministic salt here is a teaching device,
not a recommendation.

---

## Why Table 3 wins

Menu option 4 runs the same 14-word dictionary against Tables 2 and 3 and reports
how many hashes the attacker had to compute in each case.

- **Table 2:** the attacker hashes the word list once. That single pre-computed
  table breaks every matching account in the database simultaneously. Two users
  who chose the same password also produce byte-identical hashes, which leaks
  information even when neither password is cracked.
- **Table 3:** the salt differs per user, so the word list has to be re-hashed
  from scratch for every account. The attacker's cost scales with the number of
  users instead of being paid once, pre-computed rainbow tables are worthless,
  and identical passwords produce completely different stored hashes.

Salting does not make a weak password strong — `123456` still falls in both
cases. What it removes is the attacker's economy of scale.

---

## Assignment rules

- **Do not log or print passwords in real systems.** The program prints them only
  in Tables 1 and 2 output, which is the entire point of the exercise. A comment
  at the top of the file records this.
- **Never reuse the same salt.** Guaranteed by the UUID and microsecond
  timestamp, as explained above.
- **Do not use weak or reversible hashing.** SHA-256 only; no encoding such as
  base64 or ROT13, and no MD5 or SHA-1.
- **Do not store encryption keys in code.** There are no keys in this project.
  Hashing is keyless. Salts are not secrets and are correctly stored alongside
  their hashes in Table 3.
